# Phase 2 Session C — activity-aware power on the 4 tile variants

> **Headline (30-second read).** Two structurally complementary
> findings emerge once realistic switching activity is propagated
> through the existing post-route netlists:
>
> 1. **Activity-resilience on hardcoded.** TLG hc's truth-table
>    case-arms suppress the propagation of input toggling through
>    combinational logic; handopt hc's adder-tree carry chain
>    ripple-toggles on every input change. The TLG advantage on the
>    hc pair **widens from 31.2% (default-activity, 2B.5) to
>    80.25% ± 0.68% (activity-aware, 3 seeds)** — a +49 pp jump.
>    This is the single strongest result of the project.
>
> 2. **Regfile-floor effect on loadable.** Both ld variants carry a
>    ~1100-flop cfg regfile + cfg I/O whose power is largely
>    activity-invariant. That fixed floor dilutes the
>    combinational-glitching contribution that activity exposes,
>    *more* on handopt_ld (where glitching was the dominant power
>    component) than on TLG_ld. The TLG advantage on the ld pair
>    therefore **narrows from 61.5% (2B.5) to 49.07% ± 0.10%
>    (2C)** — still well above the strict ≥40% gate, but the
>    paper's framing has to acknowledge the regfile-floor effect.
>
> Both ≥25% / ≥40% gates pass with margin. **GO for Phase 3.**

---

## 1. Why this session

Phase 2B/2B.5 power numbers came from OpenSTA's default activity
model — a uniform ~0.1 toggle factor per primary input, propagated
through the netlist statistically. That's a conservative choice
that's appropriate when the workload is unknown, but reviewers will
ask whether the TLG advantage holds under realistic switching
activity. Session 2C answers that with VCD-driven activity from
random-uniform input vectors.

Crucially, **synthesis and place-and-route are unchanged.** The
existing post-route netlists, parasitics, and SDFs from 2B/2B.5 are
re-used. Only the activity input to `report_power` changes.

## 2. Methodology choices

### 2.1 VCD, not SAIF

The librelane 3.0.3 image ships OpenSTA but not `vcd2saif`. OpenSTA
in this image accepts `read_power_activities -vcd <file>` directly
(also exposed under the recommended new alias `read_vcd`). VCD-driven
and SAIF-driven activity are statistically equivalent — SAIF is just
a compressed activity summary derived from VCD — so the choice has
no effect on the reported numbers. Documented in this notes file
because reviewers will ask why we don't say "SAIF" in the
methodology.

### 2.2 Workload — random-uniform binary

1024 random 64-bit input vectors per `seed_id`, generated by
`numpy.random.RandomState(1000 + seed_id)` (a separate seed
namespace from the weight seeds — see `scripts/gen_input_vectors.py`).
The same input stream drives every variant for a given `seed_id`,
so the cross-variant comparison is apples-to-apples. The brief
locked this distribution as the SOCC methodology baseline; real-
workload (MNIST/CIFAR-10) activity moves to Phase 4 at the SoC
level.

### 2.3 Driving cadence — 1 valid + 2 idle (3 cycles/vector)

Each vector occupies 3 clock cycles: one cycle of `x_valid=1`
followed by two idle cycles. This matches the tile's 2-cycle
pipeline latency (vector i's `y_out` lands two cycles after the
x_valid pulse) and gives a sustained inference rate of one
classification per 3 cycles — what a downstream consumer would
see in steady state.

The chosen cadence pushes the per-input toggle rate to **0.166
toggles/cycle/pin** (verified by independent VCD parsing in
`results/phase2c/saif/tile_tlg_hc/tile_tlg_hc.vcd`: 32,604 toggles
across 64 input bits over 3078 cycles). That's 1.66× the OpenSTA
default of 0.1, which directly explains part of the
default→activity ratio difference (see §3.3).

### 2.4 cfg-included VCD window

For loadable variants, the testbench programs the regfile with
the seed's weight set (32 cfg writes) before driving the 1024
input vectors. The brief specified that the cfg-write phase is
part of the workload — "load weights once, then infer" — so its
activity is included in the VCD.

A diagnostic re-run on handopt_ld s0 with `$dumpvars` deferred
until *after* the cfg phase produced **702.987 mW vs the
cfg-included 706.266 mW — a 0.46% difference**. The regfile-
write transient occupies only 32 of 3104 simulation cycles
(1.0%), so its contribution is fundamentally bounded. We
therefore lock in cfg-included for all 12 measurements; the
diagnostic data is preserved at
`results/phase2c/runs/tile_handopt_ld_cfg_excl/`. **Reviewers
who probe this should be pointed at the diagnostic.**

### 2.5 Corner — `max_ff_n40C_1v95`

The corner LibreLane reports as the headline `power__total`
metric. Verified empirically: 2B's published 26.638 mW for tlg_hc
seed_id 0 matches the `max_ff_n40C_1v95/power.rpt` total; the
typical-corner `nom_tt_025C_1v80` for the same run reports 22.99
mW, which doesn't match. The `max_ff_n40C_1v95` selection comes
from OpenSTA's per-corner alphabetical iteration order in
`librelane/scripts/openroad/sta/corner.tcl`. We pin to it for
2C so the activity-aware vs default-activity comparison is
single-corner, single-axis.

### 2.6 OpenSTA flow — re-use, do not re-synthesize

`scripts/sta_power_one_corner.tcl` runs the same minimal flow
LibreLane does for the power stage:

```
read_liberty -corner <c> <sky130_fd_sc_hd__ff_n40C_1v95.lib>
read_verilog <flow/.../final/nl/<top>.nl.v>
link_design <top>
read_sdc <flow/common/tile.sdc>
read_spef -corner <c> <flow/.../final/spef/max/<top>.max.spef>
read_power_activities -scope tb_power/dut -vcd <vcd>
report_power -corner <c>
```

`Annotated 84 pin activities` for hc variants (clk, rst_n, x_in[63:0],
x_valid, y_out[15:0], y_valid) and `Annotated 155` for ld variants
(adds cfg_we, cfg_addr[5:0], cfg_wdata[63:0]). Internal nets
propagate via OpenSTA's standard statistical estimation — the
boundary annotation is the only thing that's data-driven.

Filler / tap cells appear as black-box warnings in OpenSTA's log
(identical to what the original 2B/2B.5 STAPostPNR step produced);
they have no liberty timing/power model and are correctly inert
for power calculation.

### 2.7 What did NOT change

- No re-synthesis. No re-PnR. The post-route netlist, parasitics,
  and SDFs from 2B/2B.5 are byte-identical to what was used here.
- The SDC (`flow/common/tile.sdc`) is identical. Same env knobs
  (`CLOCK_PERIOD=10`, `MAX_FANOUT_CONSTRAINT=10`,
  `MAX_TRANSITION_CONSTRAINT=0.75`,
  `SYNTH_DRIVING_CELL=sky130_fd_sc_hd__inv_2/Y`,
  `OUTPUT_CAP_LOAD=33.442`) are passed through to OpenSTA.
- The seed_id ↔ numpy-seed mapping is preserved
  (`SEED_ID_TO_NUMPY_SEED = {0: 42}`); seed_id 0 is the legacy
  Phase 2A baseline. Loadable variants reuse the seed-0 RTL and
  post-route artifacts for all seeds (RTL is seed-invariant by
  construction; only the runtime weight program differs).

### 3.4 Variance asymmetry — preserved under activity

| | hc default (2B.5) | hc activity (2C) | ld activity (2C) |
|---|---:|---:|---:|
| TLG CV         | 1.4%  | **1.16%** | 0.23% |

TLG hc retains its ~3× tighter power variance over handopt hc
under activity-aware power. Both variants are tighter than they
were under default-activity (handopt's CV dropped from 5.3% to
3.65%), but TLG remains the more predictable design across weight
distributions. **This is the same structural argument that 2B.5
made — truth-table-decomposition produces netlists whose post-
synthesis behavior depends less on specific weight bits than the
adder-tree's does — but now it holds under realistic activity, not
just the conservative default model.**

ld variants effectively show no variance because the netlist is
shared across seeds and the cfg-write transient is <0.5% of the
power signal. The 0.1–0.2% CVs are the inevitable byproduct of
slightly different random input streams interacting with slightly
different regfile contents; they're noise, not signal.

## 4. Mechanistic interpretation

### 4.1 Why hc widens: case-arm stability vs carry-chain glitching

The two combinational structures react oppositely to higher input
toggle rates:

- **TLG_hc — per-chunk truth tables.** Each chunk's `case` block
  encodes the chunk's 6→3 (or 4→3) function as a small set of
  output patterns. Many input bit-patterns map to the *same*
  case-arm output, so internal switching is decoupled from input
  switching. When input activity rises 1.66× (per-pin toggle rate
  0.166 vs OpenSTA's 0.1 default), TLG hc combinational power
  rises only ~3.4× (9.94 mW default → 33.6 mW activity). The
  super-linear factor is small.
- **handopt_hc — adder-tree carry chains.** A balanced
  popcount adder tree has carry-propagation paths that ripple-
  toggle on essentially any input change. With realistic input
  activity, every adder cell along the carry path glitches on
  most input vectors. Combinational power explodes 9.6× (17.6
  mW default → 168 mW activity).

The 3.5×-and-rising activity sensitivity ratio between handopt_hc
and TLG_hc is what drives the advantage from 31% to 80%.

### 4.2 Why ld shrinks: regfile-floor dilution

Both ld variants carry a 16×64-bit weight regfile + 16×7-bit
threshold regfile (~1136 flops total, plus the 71-pin cfg
interface). Two features of this floor:

- **Activity-invariant.** The regfile is mostly *idle* during
  inference (cfg_we = 0, weights stable), but the flops still see
  clock toggle every cycle. That clock-tree + sequential power is
  a constant contribution across any input workload.
- **Large.** For handopt_ld it is the *largest* component of
  default-activity power (167.86 mW total / ~25 mW combinational
  → ~143 mW from regfile + clock tree + cfg I/O).

When activity rises, the combinational component of handopt_ld
explodes the way handopt_hc's does (9–10× combinational growth),
but the *fixed regfile floor doesn't scale* — so the *ratio* of
activity-aware to default total is diluted to 4.21× instead of
9.59×. Meanwhile, the truth-table chunks in TLG_ld now compute
`m = x XNOR w_runtime`; with `w` runtime, the case statement
keys on `m`, which toggles freely with input. TLG_ld therefore
loses some of the activity-resilience that TLG_hc enjoys (5.58×
ratio vs 2.74×) — its truth-table compression is preserved (still
much better than handopt_ld's combinational), but the absolute
activity sensitivity is higher than TLG_hc's.

Net effect on the gap: handopt_ld's ratio shrinks more than
TLG_ld's grows, so the TLG advantage narrows from 61.5% to 49.1%.
**This is not a weakening of the activity-resilience mechanism —
it is the regfile floor being relatively activity-invariant. The
mechanism is still operating; it is just partially masked.**

### 4.3 Implications for the SOCC paper framing

- **The headline finding becomes activity resilience on hc**, not
  the default-activity 31% advantage that 2B.5 led with. Going
  from 31% → 80% under realistic activity is structurally
  surprising in a way that 31% alone was not.
- **The ld result is more honest at 49% than at 61.5%.** The
  default-activity 61.5% was inflated by the conservative input
  toggle assumption; a reviewer who reproduces under realistic
  activity will see ~49%, and the paper's claim must match that.
- **The regfile-floor mechanism is itself a contribution.** It
  tells future BNN-tile designers that a programmable design's
  power is regfile-dominated under realistic inference, so
  optimization effort should target the regfile / cfg-I/O, not
  the combinational core. This is generic guidance, not specific
  to TLG vs handopt.

## 5. What reviewers will probe (and our defenses)

- **"Why VCD instead of SAIF?"** — Statistically equivalent;
  librelane 3.0.3 doesn't ship `vcd2saif` and OpenSTA's
  `read_power_activities -vcd` consumes VCD directly. See §2.1.
- **"Why include the cfg-write phase in the activity window?"**
  — Per the brief's "load once, infer many" usage model. The
  cfg phase is 1% of the simulation window and the diagnostic
  shows it contributes 0.46% to the total (handopt_ld s0:
  706.27 mW cfg-included vs 702.99 mW cfg-excluded). See §2.4.
- **"Why max_ff_n40C_1v95 and not nom_tt?"** — Because that's
  the corner LibreLane uses for the headline `power__total`
  metric, so the activity-aware vs default-activity comparison is
  apples-to-apples. We could equally report all 9 corners; the
  ranking is stable across corners.
- **"Random-uniform inputs aren't realistic for BNN inference."**
  — Correct; that is *why* Phase 4 (SoC integration) will
  re-measure on MNIST/CIFAR-10 activity. For now, random-uniform
  is the standard methodology for tile-level BNN power studies
  (XNE, ChewBaccaNN, BTC). The 2C numbers are comparable to that
  literature.
- **"3 seeds is small."** — TLG hc CV is 1.16% across 3 seeds,
  and the per-seed advantages on the hc pair span only 1.2 pp
  (79.46 / 80.61 / 80.66). Three seeds is enough to call this
  signal not noise; 2B.5 used the same N for the same reason.
- **"Internal-net activity is propagated statistically, not
  measured."** — Standard methodology for activity-aware power
  in OpenSTA / Synopsys PT alike. Boundary-pin activity is
  measured from VCD; internal nets are propagated by the tool.
  Gate-level VCD propagation (post-synth sim, capturing internal
  switching directly) is more accurate but adds complexity for
  marginal accuracy gain — see XNE methodology.

## 6. Verdict — GO / Marginal / NO-GO

Strict criteria from the session brief:

> GO if TLG hc still beats handopt hc by ≥25% on SAIF-driven power
> AND TLG ld still beats handopt ld by ≥40% on SAIF-driven power.

- **TLG hc vs handopt hc: 80.25% ± 0.68%** — passes the ≥25%
  gate by **55.25 percentage points**.
- **TLG ld vs handopt ld: 49.07% ± 0.10%** — passes the ≥40%
  gate by **9.07 percentage points**.

Both gates pass. **Verdict: GO for Phase 3.**

Caveats that should travel forward:

- The 49% ld number is well above its gate but is more sensitive
  to methodology framing than the 80% hc number. Phase 3 work
  should keep the regfile-floor effect in mind when integrating
  the tile into a SoC — if the SoC adds further fixed
  contributions (DMA, AXI bridge, etc.), the activity-aware ld
  advantage could narrow further. The hc finding will be visible
  as a clean structural effect regardless.
- The TLG hc activity-resilience finding should lead the paper's
  abstract; the ld regfile-floor finding belongs as a secondary
  but explicit contribution. The four-quadrant table in §3.1 is
  the cleanest visual summary.

## 7. Reproduction

```bash
source scripts/env.sh

# (Re)generate input vectors and per-seed weight programs (idempotent):
python scripts/gen_input_vectors.py    # → results/phase2c/inputs/seed{0,1,2}/

# Run all 12 (variant, seed) measurements (skips already-done ones):
scripts/run_phase2c_all.sh max_ff_n40C_1v95   # ~30 s warm cache, ~10 min cold
                                              # → results/phase2c/runs/<run_key>/<corner>/

# Aggregate:
python scripts/collect_phase2c.py             # → results/phase2c/summary.{csv,md}
```

Per-(variant, seed) artifacts: `results/phase2c/runs/<run_key>/max_ff_n40C_1v95/{power.rpt,power.metrics.json}`.
VCDs: `results/phase2c/saif/<run_key>/<dut>.vcd`.
